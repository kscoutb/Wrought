=== WHAT THIS ESTABLISHES, AND WHERE IT CORRECTS THE PROMPT AND raw/16 ===

1. THERE ARE TWO INDEPENDENT SURFACES, NOT ONE, AND THEY HAVE DIFFERENT KEYS.
   - The PEER LISTING is keyed on $HOME. E3 vs F2 isolates it: identical in every respect
     except HOME, and only the real-HOME child is listed.
   - The ADDRESSABLE SOCKET is keyed on $XDG_RUNTIME_DIR. D2 vs E3 isolates it: identical
     except the runtime dir, and only the private-runtime-dir child's socket leaves the
     shared /run/user/1000/cc-socks.
   CLOSING ONE DOES NOT CLOSE THE OTHER. A private HOME alone (E3) removes the child from the
   listing while LEAVING ITS SOCKET IN THE SHARED DIRECTORY, where it is still addressable by
   path. NOT LISTED IS NOT THE SAME CLAIM AS NOT ADDRESSABLE.

2. THE PROMPT'S STATED MECHANISM IS WRONG, THOUGH ITS PRESCRIPTION IS HALF RIGHT.
   The prompt says "raw/16 established discovery is keyed under $HOME
   (~/.claude/daemon/roster.json)". The $HOME half is CONFIRMED for the listing. The
   roster.json half is REFUTED: that file read {"workers": {}} with updatedAt 2026-08-20
   throughout ALL SIX probes, including the two in which the child WAS listed. It is a stale,
   empty registry for a different mechanism and it carries no gate child.

3. raw/16's TWO REASONS FOR NOT USING A PRIVATE HOME ARE BOTH FALSE ON THIS BUILD.
   - raw/16: "a private HOME is not available to the runner because the Claude Code credentials
     live there." MEASURED FALSE. The minimal HOME for authentication is EXACTLY ONE FILE,
     ~/.claude/.credentials.json, copied in. Level 0 (empty HOME) -> is_error=true,
     terminal_reason=api_error, result "Not logged in - Please run /login". Level 1
     (+ .credentials.json) -> terminal_reason=completed. ~/.claude.json is NOT required; the
     CLI writes a fresh one into the ephemeral HOME.
   - raw/16 probe 3: "the private directory was left completely empty - no socket was created
     in it - and the child was still listed. Discovery is therefore not keyed on
     XDG_RUNTIME_DIR." On 2.1.250 the private runtime dir DOES receive a cc-socks/ directory
     and the child's socket IS created there (D2). Probe 3's child was still listed because it
     kept the REAL HOME, which is the listing key - not because the runtime dir did nothing.

4. A PRIVATE XDG_RUNTIME_DIR MUST BE APPLIED TO THE CLAUDE PROCESS ONLY, INSIDE THE SCOPE.
   Setting it for the whole invocation breaks the launcher, measured (probe C1):
     stderr: "Failed to connect to user scope bus via local transport: No such file or directory"
     stdout: 0 bytes, no result JSON
   `systemd-run --user` needs the REAL runtime dir to reach the user bus. The working form puts
   the override between the scope and the binary:
     systemd-run --user --scope ... /usr/bin/env XDG_RUNTIME_DIR=<private> <claude> -p ...

=== RESIDUAL, STATED PLAINLY ===

  The isolation is ONE-DIRECTIONAL. A gate child cannot be found or addressed by the operator's
  sessions. The reverse is not closed: the child's own filesystem view still includes
  /run/user/1000/cc-socks, so a child that chose to could see the operator's session sockets.
  Probe D2's step-1 output shows exactly this - it listed 13774.sock, this session. Whether it
  could USE that is untested and out of this gate's scope; it is recorded because "isolated"
  without a direction is the kind of claim this project keeps having to retract.
