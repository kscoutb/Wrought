=== FINDINGS (b) ===
1. THERE IS NO PERMISSION MODE LITERALLY NAMED "default-deny". `claude --permission-mode` on
   2.1.238 offers exactly: acceptEdits, auto, bypassPermissions, manual, dontAsk, plan.
2. TWO MODES ARE DEFAULT-DENY-WITH-ALLOWLIST: `dontAsk` and `manual`. Both refused an
   un-allowlisted Bash call, and both HONOURED an allowlist when one was given, down to the
   granular `Bash(touch:*)` form. A granular allowlist that does not cover the command
   (`Bash(git *)` vs a `touch`) correctly refused. => the runner uses `dontAsk`.
3. TWO MODES SILENTLY AUTO-APPROVE: `acceptEdits` and `auto` BOTH RAN the un-allowlisted Bash
   command. `--allowedTools` is NOT a containment boundary under those modes. Naming a mode
   "acceptEdits" does not mean it accepts only edits.
4. `plan` refused, but is not a containment mode — it refuses everything, so no gate can work.
5. `--tools Read` (removing Bash from the built-in set entirely) refused even under acceptEdits.
   This is a STRONGER boundary than --allowedTools and is independent of permission mode.
6. `--disallowedTools Bash` beat `--allowedTools Bash`: DENY WINS OVER ALLOW.
7. **EVERY CASE EXITED rc=0 — INCLUDING EVERY DENIED ONE.** The child's exit status does not
   distinguish "did the work" from "was refused". The runner MUST classify on the result JSON
   (`is_error`, `subtype`, `permission_denials`), never on the exit integer. This is the same
   shape as the project's own rule that bwrap-proxied exit integers are ambiguous
   (CLAUDE.md, docs/03 S10.7) — it recurs here for an unrelated reason.
